# PRD — blog-publisher

- 작성일: 2026-08-17
- 상태: 초안 (구현 착수 전)

---

## 1. 한 줄 정의

Claude Code / Claude Desktop 안에서 대화하듯 [`jiny-log`](../../jiny-log/) 블로그에 글을 발행하는 MCP 서버.

## 2. 왜 만드는가

**글쓰기와 발행 사이의 마찰이 블로그를 죽인다.**

[`jiny-log/docs/PRD.md`](../../jiny-log/docs/PRD.md) §6에서 발행 빈도를 1순위 지표로 잡았다. 그런데 통상적인 발행 절차는 이렇다:

```
에디터로 파일 생성 → frontmatter 손으로 작성 → 슬러그 고민 → 이미지 옮기기
→ 경로 확인 → git add/commit/push → 배포 확인
```

트러블슈팅은 **디버깅이 끝난 직후**에 써야 가장 정확하다. 그 시점에 위 절차가 끼면 "나중에 쓰지"가 되고, 나중은 오지 않는다.

이 서버는 그 절차를 **대화 한 줄**로 줄인다. 이미 Claude Code에서 디버깅하고 있었다면, 맥락이 살아있는 그 자리에서 바로 초안이 나간다.

## 3. 사용 시나리오

### S1. 방금 해결한 문제를 글로 남긴다 (주 시나리오)

```
사용자: 방금 고친 hydration 문제 블로그 초안으로 만들어줘
  → create_draft: frontmatter 검증 → 브랜치 커밋 → PR 생성
  → 반환: Vercel 프리뷰 URL
사용자: (프리뷰 확인) 좋다, 발행해줘
  → publish_post: draft=false → main 머지
  → 반환: https://<domain>/ko/posts/nextjs-hydration-mismatch
```

**초안 생성과 발행이 반드시 두 턴으로 갈린다.** 이것이 이 도구의 핵심 안전 장치다.

### S2. 발행된 글의 오타·내용 수정

```
사용자: 그 글에서 Node 버전 24.10으로 잘못 적었어, 24.11로 고쳐줘
  → get_post (현재 commitSha 확보) → update_post
  → updated 날짜 자동 각인, date는 불변
```

### S3. 이미지 첨부

```
사용자: 이 스크린샷 글에 넣어줘
  → upload_asset: public/images/<slug>/ 에 커밋 → 상대 URL 반환
  → update_post 로 본문에 삽입
```

### S4. 발행 전 검증만

```
사용자: 이 frontmatter 문제 없는지 봐줘
  → validate_frontmatter: 아무것도 쓰지 않고 오류 목록만 반환
```

### S5. 영어 번역 추가

```
사용자: 그 글 영어 버전도 올려줘
  → 같은 슬러그, locale=en 으로 create_draft
```

## 4. 성공 기준

| 지표 | 목표 |
|---|---|
| 초안 생성 소요 | 대화 1턴, 30초 이내 |
| 발행까지 총 소요 | 프리뷰 확인 포함 5분 이내 |
| **의도치 않은 발행** | **0건** — 가장 중요한 지표 |
| 잘못된 frontmatter가 main에 도달 | 0건 |
| 기존 글 의도치 않은 덮어쓰기 | 0건 |
| 발행 실패 시 진단 가능성 | 오류 메시지만 보고 원인 파악 가능 |

**"편리함"보다 "사고 0건"이 상위 목표다.** 발행이 한 턴 더 걸리는 것은 감수하지만, 미완성 글이 공개되는 것은 감수하지 않는다.

## 5. 범위

### v1

- 읽기: `list_posts`, `get_post`
- 검증: `validate_frontmatter`, `generate_slug`
- 쓰기: `create_draft`, `publish_post`, `update_post`, `unpublish_post`, `delete_post`
- 자산: `upload_asset`
- stdio 트랜스포트, 로컬 실행
- `MCP_DRY_RUN` 모드
- ko/en 이중 로케일 지원

상세 명세는 [`TOOLS.md`](./TOOLS.md).

### v2 이후

- 이미지 자동 최적화 (WebP/AVIF 변환, 리사이즈)
- 예약 발행
- 발행 후 SEO 체크 자동 실행
- 글 통계 조회 (조회수·크롤러 히트)

### 명시적 비목표

| 비목표 | 이유 |
|---|---|
| **웹 에디터 / 관리자 UI** | MCP 도구가 인터페이스다. UI를 만들면 이 프로젝트의 존재 이유가 사라진다 |
| **다중 블로그 지원** | 저장소 1개 전용. 범용화하면 설정과 실패 모드가 폭증한다 |
| **원격 HTTP 서버 배포** | stdio 로컬 실행. 네트워크에 노출하는 순간 인증·레이트리밋·감사 로그가 전부 필요해진다 |
| **글 내용 생성** | 이 서버는 **운반 도구**다. 글은 사용자와 Claude가 대화로 쓴다. 서버가 내용을 만들지 않는다 |
| **DB / CMS 연동** | 콘텐츠는 git에 산다. [`ARCHITECTURE.md`](./ARCHITECTURE.md) §1 참조 |

## 6. 제약

| 제약 | 내용 |
|---|---|
| 발행 반영 지연 | git push → Vercel 빌드 → 배포까지 **1~3분**. 즉시성이 필요한 유스케이스가 아니므로 수용 |
| GitHub API 레이트리밋 | 개인 사용량에서는 무관. 다만 폭주 방지용 서킷 브레이커는 둔다 |
| 프리뷰 URL 확보 | Vercel이 PR에 배포를 붙이는 데 시간이 걸린다. URL을 예측 생성하거나 PR 링크로 폴백 |
| 클라이언트 프로토콜 | Claude Code/Desktop이 실제로 협상하는 리비전에 맞춘다. **Phase 0에서 실측 후 SDK 세대 확정** ([`CLAUDE.md`](../CLAUDE.md) ⚠️ 절) |

## 7. 핵심 리스크

| 리스크 | 영향 | 대응 |
|---|---|---|
| **프롬프트 인젝션으로 인한 의도치 않은 발행** | 미완성/조작된 글 공개 | **draft-by-default + 발행 도구 분리.** 생성이 발행으로 이어지는 경로를 만들지 않는다 |
| **오래된 컨텍스트로 덮어쓰기** | 기존 글 손실 | `commitSha` 낙관적 동시성. 불일치 시 거부 |
| **경로 이탈 쓰기** | 저장소 임의 파일 조작 | 핸들러 내부 경로 정규화 + allowlist |
| **토큰 유출** | 저장소 쓰기 권한 탈취 | 로그·반환값·에러에서 제외. 최소 권한 PAT. 상세는 [`SECURITY.md`](./SECURITY.md) |
| **LLM이 사실을 지어냄** | 틀린 버전·없는 URL이 발행됨 | 서버가 막을 수 없다. [`WRITING-GUIDE.md`](../../jiny-log/docs/WRITING-GUIDE.md) §7 + 사람의 프리뷰 확인이 유일한 방어선 |

> 마지막 항목은 정직하게 남긴다. **이 서버는 내용의 진위를 검증할 수 없다.** 형식(frontmatter, 경로, 상태 전이)만 보장한다. 그래서 프리뷰 확인 단계를 없애지 않는다.
